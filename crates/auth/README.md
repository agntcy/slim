# AGNTCY Slim Auth

[![License](https://img.shields.io/badge/license-Apache%202.0-blue.svg)](LICENSE)

This crate provides authentication and authorization capabilities for Agntcy SLIM,
with a focus on JWT (JSON Web Token) authentication and SPIFFE/SPIRE integration.

## Features

- JWT token creation and verification
- Builder pattern for fluent JWT configuration
- Flexible key resolution for JWT verification
- Support for OpenID Connect Discovery
- JWKS (JSON Web Key Set) integration
- Asynchronous verification for improved performance
- **SPIFFE/SPIRE integration for zero-trust workload identity**
  - X.509 SVID automatic rotation
  - JWT SVID with configurable audiences
  - Native Workload API integration
  - Support for federated trust domains
- **OIDC identity bound to an app-supplied MLS signing key, via DPoP (RFC 9449)
  plus a key attestation**
  - Maps an SSO user onto the MLS credential, with no custom claim mapper
  - RFC 7638 JWK thumbprints for `cnf.jkt` verification
  - Authorization Code + PKCE and refresh-token grants, both DPoP-proofed
  - MLS keys stay owned by `mls-rs`: rotation, restore and per-session keys need
    no new login

## OIDC with DPoP

`OidcTokenProvider` / `OidcVerifier` make the MLS identity the identity provider's
`sub` — the signed-in person — instead of a value minted per application instance.
See [Authentication](../../docs/content/slim/architecture/authentication.md) for
the user-facing description; this section covers the crate internals.

**Requires an RFC 9449 provider** (Keycloak 26.4+ for official DPoP support;
experimental from 23.0, enabled with `--features=dpop`).

### Two keys

`cnf.jkt` is written by the IdP at issuance and cannot be recomputed locally, so
one token can only ever confirm the one key its grant was minted under. Binding
the MLS key to it directly would therefore force the *login* to generate the MLS
key — and then rotation, snapshot restore and per-session keys each need a new
browser login. So there are two keys:

| | Generated by | Constrained by | Lifetime |
|---|---|---|---|
| **identity key** (`K_pop`) | `slimctl login`, once | JOSE — always P-256 (`ES256`) | the refresh-token chain |
| **MLS leaf key** (`K_leaf`) | the `mls-rs` crypto provider, any number of times | the active MLS ciphersuite | one epoch range |

`K_pop` is what the IdP proofs and `cnf.jkt` names; it is never handed to
`mls-rs`. It signs a 300-second attestation naming `K_leaf`, which the credential
carries. Installing a new `K_leaf` just mints a new attestation — no IdP contact.

Because `K_leaf` rides inside the attestation payload as opaque bytes, it is never
parsed as a JWK and needs no JOSE mapping at all. The
`curve25519`/`enforce_pqc` interaction therefore no longer touches the identity
path: `Mls::build_client`'s ciphersuite check still guards a restored snapshot,
but the identity key cannot be the wrong curve because nothing but JOSE picks it.

### Module map

| Item | Purpose |
|------|---------|
| `dpop::build_proof` | Construct the `dpop+jwt` proof sent to the token endpoint |
| `dpop::jwk_thumbprint` | RFC 7638 thumbprint of a public key — the `cnf.jkt` value |
| `dpop::build_key_attestation` | Sign `{pubkey: K_leaf, iat, exp, jti}` under `K_pop` |
| `dpop::verify_key_attestation` | Check that JWS and return `(signer_jkt, leaf_public_key)` |
| `dpop::IdentityKey` | Holds `K_pop` and the current `K_leaf`; caches the attestation |
| `oidc::post_token_request_with_dpop` | Token-endpoint POST carrying a proof, with the RFC 9449 §8 nonce retry |
| `OidcTokenProvider::exchange_authorization_code` | Authorization-code grant; mints the binding |
| `OidcTokenProvider::install_identity_keys` | Adopt `K_pop` from `slimctl login --dpop-credentials-file <path>`. Refuses a key the live token is not bound to |
| `OidcTokenProvider::install_signature_keys` | Adopt `K_leaf` from the MLS layer. Unconditional — this is what makes rotation free |

`dpop` is free of `jsonwebtoken` and `reqwest` so it also compiles for `wasm32`,
where thumbprints are still needed but those crates are unavailable.

### How the key reaches the verifier

A DPoP token commits to `K_pop` only as a one-way hash, and the MLS layer needs
`K_leaf`. The holder therefore presents an attestation alongside the token, in
the credential `get_token()` returns:

```text
<access token>~<attestation JWS>
```

The attestation is a JWS whose protected header carries `K_pop` inline as `jwk`
(so no key distribution is needed) and whose payload names `K_leaf`:

```json
{ "typ": "slim-key-att+jwt", "alg": "ES256", "jwk": { "crv": "P-256", ... } }
{ "pubkey": "<base64url K_leaf>", "iat": 1756713600, "exp": 1756713900, "jti": "..." }
```

`OidcVerifier` splits the credential, validates the token via JWKS, then requires
both halves of the chain:

1. the attestation verifies under the key in its own `jwk` header, **and**
2. that key's thumbprint equals `cnf.jkt`, so the IdP vouched for the signer.

Only then is `K_leaf` surfaced as an ordinary `pubkey` claim. Everything
downstream — `IdentityClaims`, MLS `validate_member`, e2e header signature
checks — reads a normal raw-public-key claim and needs no awareness of any of
this.

Step 2 is what makes the scheme work. Every group member holds the whole ratchet
tree, so any member can read a peer's credential verbatim; an envelope signed by
`K_leaf` itself would let them strip it and re-sign under their own key. Only a
signature by a key the IdP already named distinguishes the owner's choice of
`K_leaf` from an onlooker's. `typ` is checked for the same reason: a DPoP proof is
the same shape over the same key, and without the check one captured from a token
request would pass as an attestation.

This rides in the existing `SLIMHeader.identity` field, which is already an
opaque provider-specific string (`SharedSecret` puts a colon-delimited MAC format
there, not a JWT). No wire-format change was required — which matters, because
`prost` drops unknown fields and relay nodes re-encode forwarded messages, so a
new proto field would be silently stripped by any node running an older build.

A credential with no `~` is a plain bearer token and takes the unchanged path, so
transport-auth use of `OidcVerifier` is unaffected.

### Deployment constraint: token exchange

`cnf.jkt` is only as strong as the weakest token-re-minting path the IdP offers,
and this design publishes the bound token into the MLS ratchet tree where every
member can read it — outside DPoP's own threat model, which assumes the token
stays with its holder.

Measured on Keycloak 26.4: standard token exchange (RFC 8693) re-binds a
DPoP-bound subject token to whatever key the request proofs, preserving `sub`,
**contrary to its documentation**. Anyone holding a peer's access token and the
app's client credentials could therefore mint a token naming that peer bound to
their own key.

So, for the client used as an MLS identity:

- do **not** enable standard token exchange on it, and
- keep it a **public** client (public clients cannot exchange at all, and cannot
  re-bind a refresh token either).

Both hold by default. The risk is a later realm change switching one on with
nothing in SLIM to notice.

## Testing

This crate includes comprehensive unit tests and integration tests:

- **Unit tests**: Test individual components and error handling
- **Integration tests**: Test real interactions with SPIRE server and agent using Docker containers

### Running Tests

```bash
# Run unit tests only
cargo test --lib

# Run integration tests (requires Docker)
cargo test --test spiffe_integration_test -- --ignored --nocapture

# Run all tests
cargo test -- --include-ignored
```
